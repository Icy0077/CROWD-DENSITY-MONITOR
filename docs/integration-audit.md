# CloudCrowdAnalytics Integration Audit

This audit is based on the current repository state and checks the implementation without adding new features or modifying production files.

## Findings

### Resolved critical issue

- Fixed: the dependency file was saved as UTF-16 with a BOM, which prevented standard pip reads in clean environments. It was re-encoded to UTF-8 and verified with a successful install check.

| Issue | File | Severity | Status | Suggested fix |
| --- | --- | --- | --- | --- |
| `requirements.txt` is encoded as UTF-16 with a BOM instead of plain UTF-8/ASCII. This breaks normal `pip install -r requirements.txt` workflows and can prevent dependency installation in CI and local environments. | `requirements.txt` | Critical | Fixed | Re-save the file as UTF-8 without BOM, keep one requirement per line, and verify the installation command succeeds before shipping. |
| The project used inconsistent telemetry field names across edge, MQTT, Lambda, DynamoDB, and API boundaries. Data was emitted as `facility_id`, `inflow`, `outflow`, and `wait_time`, but the schema expects `location_id`, `people_in`, `people_out`, and `estimated_wait_minutes`. | `edge/mqtt/publisher.py`; `cloud/lambda/handler.py`; `cloud/dynamodb/database.py`; `cloud/api/routes.py`; `frontend/src/services/api.js` | Critical | Fixed | Normalize every payload to the canonical schema from `docs/telemetry-schema.md`, while accepting legacy aliases during parsing to maintain compatibility. |
| The API response and stored DynamoDB state did not compute occupancy percentage or status consistently with the documented thresholds. | `cloud/dynamodb/database.py`; `cloud/api/routes.py`; `cloud/lambda/handler.py` | Critical | Fixed | Calculate `occupancy_percentage` from `occupancy / capacity * 100` and set `status` to `green`, `yellow`, or `red` using the documented thresholds. |
| Privacy masking is effectively a no-op: `PrivacyDrop.drop()` deletes the frame object and returns `None`, so no frame anonymization or face/body blurring is actually performed. | `edge/privacy/privacy_drop.py` | Critical | Open | Replace the stub with a real anonymization routine (e.g., blur or pixelate sensitive regions) and return a sanitized frame instead of `None`. |
| ByteTrack implementation is missing. `edge/tracking/tracker.py` exists but is empty, so there is no real tracking logic or integration point for the line-crossing detector. | `edge/tracking/tracker.py` | High | Implement the tracker wrapper or remove the stub and call the Ultralytics built-in tracker explicitly with a validated config file. |
| The YOLO detector updates occupancy using a local `self.occupancy` counter without a stable reset/epoch boundary. `detect()` adds `IN - OUT` counts each frame, which can drift or double-count if the same person crosses multiple frames or if detection output is noisy. | `edge/vision/detector.py` | High | Use per-frame or per-track crossing state that is reset correctly for each detection window, and gate occupancy updates on confirmed track transitions rather than raw box counts. |
| The detector uses `YOLO.track(..., tracker="bytetrack.yaml")` but the project does not provide a tracked config contract or a custom tracker wrapper. The current implementation is dependent on the Ultralytics tracker config being present and valid in the runtime environment. | `edge/vision/detector.py` | Medium | Add a project-owned tracker config file and document the expected tracker path; validate the runtime config before deployment. |
| The telemetry schema is inconsistent across the system. Edge telemetry uses `facility_id`, `inflow`, `outflow`, and `wait_time`, while the API schema doc expects `location_id`, `people_in`, `people_out`, and `estimated_wait_minutes`. | `edge/mqtt/publisher.py`; `cloud/lambda/handler.py`; `docs/telemetry-schema.md` | Critical | Choose one canonical telemetry schema and align all producers, storage, and consumers to it. Update sample payloads and API docs together. |
| DynamoDB state schema is mismatched with the Lambda/edge telemetry schema. `OccupationStateStore.save_state()` validates `facility_id`, `occupancy`, `wait_time`, but the incoming telemetry payload includes `inflow`, `outflow`, and `timestamp` and does not include `capacity` or `status`. | `cloud/dynamodb/database.py`; `cloud/lambda/handler.py` | High | Expand the stored schema to match the production contract and normalize all fields before persisting to DynamoDB. |
| API responses use the wrong field names for the documented schema. `_mock_telemetry()` and `_telemetry_from_state()` return `location_id`, `people_in`, `people_out`, and `estimated_wait_minutes`, but AWS Lambda and MQTT payloads emit `facility_id`, `inflow`, `outflow`, and `wait_time`. | `cloud/api/routes.py` | High | Standardize the data contract in one place and adapt both the API serializer and the backend store to the same naming model. |
| The API layer silently falls back to mock data when `DYNAMODB_TABLE` is missing. This masks deployment and configuration errors and makes production behaviour appear healthy while data is unavailable. | `cloud/api/routes.py` | Medium | Fail fast with a clear configuration error or log a warning with explicit monitoring instead of returning synthetic telemetry by default. |
| Frontend API integration is incomplete and inconsistent. `fetch('/telemetry/latest')` has no `facility_id` query parameter, but the local server expects `?facility_id=...`, and the API contract is different from the front-end mock objects. | `frontend/src/services/api.js`; `cloud/api/local_server.py` | High | Align the frontend request contract with the server route contract and map the response fields to the dashboard model explicitly. |
| The dashboard is hardcoded to demo values and uses synthetic data even when the API is configured. This makes the UI behave like a mock dashboard rather than a live telemetry system. | `frontend/src/App.jsx` | Medium | Replace the hardcoded `initialDashboardData` with real API state handling and make the UI clearly reflect live data vs demo fallback. |
| AWS IoT, Lambda, DynamoDB, and API modules are not wired into a single working pipeline. The project contains separate implementations but no concrete integration path, deployment config, or end-to-end orchestration. | `cloud/iot/device.py`; `cloud/lambda/handler.py`; `cloud/dynamodb/database.py`; `cloud/api/local_server.py` | High | Define a single message-flow contract and implement the actual AWS ingestion path: edge -> MQTT -> IoT rule/topic -> Lambda -> DynamoDB -> API. |
| The MQTT publisher defaults to `localhost:1883` and does not enforce secure broker configuration. This is risky for deployment and can silently fail in production or expose data in plaintext. | `edge/mqtt/publisher.py` | Medium | Require explicit broker credentials/secure transport configuration and treat `localhost` as a development-only default. |
| AWS credentials and certificate settings are environment-based but there is no secure configuration management or secret injection strategy in the repo. The project relies on raw environment variables with no validation beyond required names. | `cloud/iot/device.py` | Medium | Use a secure secret manager or deployment secret store, and validate cert paths and credentials before connection attempts. |
| Project-level tests and validation stubs are empty. There are placeholder files for detection, tracking, privacy, and integration tests, but no actual assertions or pipeline checks. | `tests/test_detection.py`; `tests/test_tracking.py`; `tests/test_privacy.py`; `integration/pipeline_test.py` | Medium | Implement regression tests for each critical path: detection counts, privacy masking, tracker crossings, and end-to-end telemetry flow. |
| `edge/config/settings.py`, `cloud/api/routes.md`, and other config/docs placeholders are empty stubs rather than complete configuration or API documentation. | `edge/config/settings.py`; `cloud/api/routes.md` | Low | Fill in environment and route documentation or remove unused placeholders to reduce confusion. |

## Summary

The project is partially scaffolded but not yet a coherent working integration. The highest-risk issues are the schema drift between edge, cloud, and frontend; the non-functional privacy filter; the empty ByteTrack implementation; and the broken dependency file encoding. These need to be addressed before any production use or end-to-end validation.
